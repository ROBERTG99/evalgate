# Known limitations

What is not done, or done with a documented gap. Each entry names the reason.

- **Third-party LLM metrics bypass the gateway.** `ragas:` and `deepeval:` metrics that call an LLM use those libraries' own clients, so they skip evalgate's cache, PII redaction, `LIVE_EVAL_BUDGET_USD` and the offline socket guard. Use their non-LLM metrics in gates (ExactMatch, StringPresence, NonLLMStringSimilarity, BLEU/ROUGE; DeepEval ExactMatchMetric, PatternMatchMetric); the offline test suite only exercises those.
- **Release binaries are not checksum-verified.** `scripts/install_tools.sh` downloads hadolint, trivy and shellcheck over HTTPS from GitHub releases by pinned version but does not verify SHA-256 sums; actionlint and gitleaks are built from the Go module proxy, which is checksum-verified by `sum.golang.org`.
- **No recorded LLM cassettes.** No provider key was available during the build, so `tests/fixtures/llm/` holds no cassettes and the provider adapters are tested against response fixtures written in the documented API shapes (`tests/fixtures/provider_responses/`), not recordings.
- **Judge labels are by construction.** All 260 judge labels were generated with known answers; the maintainer review of 40 labels is pending (see `PROGRESS.md`). See ADR-0006 for what this does and does not prove.
- **`gate_audit` only covers `evalgate check` runs on the same machine.** CI keeps `runs.duckdb` as a 14-day artifact; there is no central audit store.
- **Percentile bootstrap under-covers at small n.** The §11 coverage check (400 simulated datasets of 150 correlated binary cases, 10,000 resamples) measures 0.96, but the same simulation gives about 0.89 for 60 cases with a near-perfect baseline (0.97 → 0.95), about 0.84 for 20 cases and about 0.68 for 10 cases, the smallest number of pairs the gate accepts (`MIN_PAIRED`) (`evals/reports/bootstrap-coverage.json`, scenarios table in `evals/REPORT.md`). These scenarios have a real drop, so they measure coverage, not the false-alarm rate. In the near-perfect regime the misses fall mostly on the side that understates a drop, so the main cost is lower power (missed regressions); the false-alarm rate in these regimes was not measured by `make eval`. At n <= 60 one flipped case is already at least 1.67 pp, so `--max-regression-pp` 1.0 adds no protection there. Use test splits larger than 60 when a metric sits near 1.0; a BCa or exact-binomial interval is the next improvement.
- **No multiple-comparison adjustment.** Each gated metric is tested on its own at 95%. With several gated metrics at the margin (extract gates 6), the chance that at least one shows a false regression is higher than for one metric ([design FAQ, question 2](design-faq.md#2-how-are-multiple-comparisons-handled)).
- **The meta-evaluation regressions are coarse.** The toy targets are deterministic and the injected regressions are large; most also fail an absolute threshold or a budget. 30/30 detected and 0/20 false alarms give exact 95% bounds of [0.884, 1.0] and [0, 0.168] (`evals/reports/meta-eval.json`), so the §11 targets are met as point estimates, not with certainty.
- **`.env.example` is also unreadable for Claude Code.** `.claude/settings.json` denies `Read(./.env.*)` to keep real environment files away from the agent; permission rules have no exceptions, so the committed `.env.example` is covered too. Read it with `cat` from a terminal, or narrow the rule to named files if that matters more than the blanket deny.
- **The live budget can be overshot by the calls already in flight.** `SpendGuard` checks the budget before each judge call and adds the cost after it returns (`src/evalgate/llm/gateway.py`, `src/evalgate/budget.py`), so up to `EVALGATE_JUDGE_CONCURRENCY` (default 4) concurrent calls can finish past `LIVE_EVAL_BUDGET_USD`. The upfront estimate stops runs that are expected to exceed it before any call.
- **PII redaction is pattern based.** It catches emails, common phone formats and Luhn-valid card numbers, not names, addresses or national ids (`docs/security.md`, LLM02).
- **Synchronous metrics run on the event loop.** Built-in metrics are fast, but a slow synchronous custom metric (or the DeepEval and Ragas adapters) blocks other cases while it scores, which inflates their measured latency. Make expensive custom metrics `async` (`ascore`).
- **A budget abort waits for the cases already scheduled.** When one case raises the live budget abort (exit 3), the runner still lets the other in-flight cases finish before it exits; the gateway refuses further paid calls, so the extra cost is bounded by the calls already in flight (see above).
- **`json_schema` `schema_path` resolves against the working directory only**, while datasets also fall back to the suite's folder. Run evalgate from the repository root, or give an absolute path.
- **LangGraph step timestamps are taken when a node finishes**, not when it starts (`src/evalgate/targets/langgraph.py`); durations are correct.
- **Likert judges trust the judge's score.** For `likert5` rubrics the case value is the judge's `score`, not cross-checked against its `verdict`, so `verdict: fail` with `score: 0.9` passes a 0.75 `pass_at`. Calibration measures agreement on the verdicts; a disagreement check is a candidate improvement.
- **Custom metrics that return a `MetricScore` keep their own `passed`.** The value is clipped to [0, 1] (non-finite values are metric errors) but `passed` is not re-derived from `pass_at`; return a float to let evalgate decide.
- **`render_markdown` without a check result** shows each metric's threshold result only; the CLI and the action always pass the `evalgate check` result, which includes metric errors, budgets and run health.
- **An explicit empty or `null` requirement passes.** `contains_all` with `expected: []` or `null`, and `tool_calls` with `expected.tools: []` or `null`, require nothing and score 1.0; only an absent field is a problem.
